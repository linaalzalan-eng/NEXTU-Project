**ما أُنجز فعليًا** (المهام P1-T01 إلى P1-T15 في `docs/IMPLEMENTATION_PLAN.md`):
- مستودع Git مستقل للمشروع، مع `.gitignore` يحمي الأسرار.
- 13 وثيقة في `docs/` تغطي: لماذا نبني المنتج، وماذا نبني، وكيف نبنيه، وكيف نختبره، وبأي ترتيب.

- حسم القرارين المفتوحين OD-01 (تأكيد البريد) وOD-02 (استعادة كلمة المرور).

**ما لم يحدث في هذه المرحلة:** لا يوجد `package.json` ولا `src/`. هذه بدأت في المرحلة 2.

## 2. الملفات والمجلدات

### وثائق المنتج (ماذا نبني؟ ولماذا؟)
- `docs/PROJECT_INTENT.md`: الرؤية والجمهور والفلسفة ("منافسك الوحيد هو نسختك السابقة").
- `docs/MVP_SCOPE.md`: ما هو داخل الـ MVP وما هو خارجه صراحةً (لا AI، ولا gamification، ولا مهام متكررة...). أي ميزة غير مذكورة فيه لا تُبنى.
- `docs/PRD.md`: **المصدر الوحيد** لقواعد العمل BR-01 إلى BR-14، مثل طريقة حساب نسبة الإنجاز وتعريف الأسبوع.

- `docs/USER_FLOW.md`: مسارات المستخدم خطوة بخطوة (التسجيل، إنشاء مهمة، الحذف، الحالات الفارغة...).

### وثائق هندسية (كيف نبني؟)
- `docs/SRS.md`: المتطلبات الوظيفية FR، وغير الوظيفية NFR (أداء، أمان، وصول)، وقواعد التحقق VR.
- `docs/ARCHITECTURE.md`: الطبقات وبنية المجلدات المعتمدة على الـ features، وكيف يتصل كل جزء بالآخر.
- `docs/DATABASE_SCHEMA.md`: جدول `tasks` الوحيد، والقيود (constraints)، والفهرس، وسياسات RLS.
- `docs/API_CONTRACTS.md`: توقيعات دوال الـ services (`listTasks`، `createTask`...) وأنواع الأخطاء.

### وثائق الجودة والتنفيذ
- `docs/TESTING_PLAN.md`: معرّفات الاختبارات UT (وحدة)، وCT (مكوّن)، وIT (تكامل)، وST (أمان)، وقائمة الإطلاق.
- `docs/IMPLEMENTATION_PLAN.md`: المراحل الست ومهام كل مرحلة ومعايير اكتمالها.
- `docs/PROGRESS.md`: الحالة الحالية ونتائج الاختبارات.
- `docs/DECISIONS.md`: سجل القرارات D-01 إلى D-20 في هذه المرحلة (وصل لاحقًا إلى D-25).

### إعدادات Claude Code
- `CLAUDE.md`: التعليمات الدائمة لطريقة العمل (يُقرأ في بداية كل جلسة).
- `.claude/settings.json`: صلاحيات تمنع قراءة ملفات `.env` وتطلب الإذن قبل `git commit` و`git push` والنشر على `vercel`.
- `.claude/agents/code-reviewer.md`: مراجع للقراءة فقط (`Read, Grep, Glob`) يُشغَّل في نهاية كل مرحلة.

### ملفات الجذر
- `.gitignore`: يستبعد `node_modules/` و`dist/` وكل ملفات `.env*` ما عدا `.env.example`.
- `README.md`: نظرة عامة وروابط الوثائق.

## 3. التقنيات والمكتبات

لم تُثبَّت أي مكتبة في هذه المرحلة، لكن **اختيار الـ stack** حُسم ووُثّق فيها:

- **React + Vite، بـ JavaScript فقط:** لأنك Frontend Developer تعرف React، وهدف المشروع تعلّم ما حوله لا لغة جديدة.
- **Tailwind CSS v4:** تصميم سريع، مع utilities منطقية تدعم RTL (`ms-` بدل `ml-`).
- **React Router (declarative mode):** أبسط أسلوب للتوجيه للمتعلّم (D-16).
- **Recharts:** رسوم بيانية بمكوّنات React (المرحلة 4).
- **Supabase (Auth + PostgreSQL + RLS):** backend جاهز بلا server نكتبه بأنفسنا (المرحلة 5).
- **Vitest + React Testing Library:** اختبارات تعمل مع Vite مباشرة (المرحلة 3).
- **Vercel:** نشر مجاني لتطبيق SPA (المرحلة 6).

**ما رفضناه عمدًا ولماذا:**
- لا Redux/Zustand/React Query: الـ Context والـ custom hooks تكفي لتطبيق بهذا الحجم وتعلّم أساسيات React (D-07).
- لا مكتبة تواريخ: التواريخ نصوص `"YYYY-MM-DD"` مع دوال صغيرة مختبرة (D-10).
- لا مكتبة i18n: قاموس داخلي صغير يكفي (D-02).

## 4. شرح "الكود": كيف ترتبط الوثائق ببعضها

لا يوجد كود تطبيق، لكن الوثائق مصمّمة كنظام مترابط بالـ **معرّفات (IDs)**. هذا أهم ما يجب فهمه في المرحلة 1.

### نظام المعرّفات
كل معرّف يُعرَّف في وثيقة **واحدة فقط**، وبقية الوثائق تشير إليه ولا تكرره:
- `BR-xx` في `PRD.md` (قواعد العمل).
- `FR-xx` و`NFR-xx` و`VR-xx` في `SRS.md`.
- `US-xx` في `USER_STORIES.md`.
- `UT/CT/IT/ST-xx` في `TESTING_PLAN.md`.
- `D-xx` في `DECISIONS.md`.
- `Px-Tyy` في `IMPLEMENTATION_PLAN.md`.

### مثال حقيقي: كيف تتحول قاعدة واحدة إلى كود واختبار
قاعدة نسبة الإنجاز اليومية، كما هي في `docs/PRD.md`:

```text
BR-01 — Daily completion rate
rate(D) = completed(D) / total(D) × 100 ... If total(D) = 0, the rate is null (BR-06).
```

ثم تتبّعها في بقية الوثائق:
1. `API_CONTRACTS.md` §5 يحدد أن الدوال التحليلية pure functions تُرجع رقمًا من 0 إلى 100 أو `null`.
2. `ARCHITECTURE.md` يحدد مكانها: `src/lib/stats.js` (`toRate`، `getDailyStats`).
3. `TESTING_PLAN.md` يحدد اختبارها: UT-04.
4. `IMPLEMENTATION_PLAN.md` يحدد متى تُبنى: المهمة P4-T02.

وفي المرحلة 2 ظهر أثر BR-06 في الواجهة: `ProgressBar` يقبل `value = null` ويعرض نصًا بدل "0%". التفاصيل في `PHASE_2_EXPLAINED.md`.

### مثال حقيقي: الأمان مُصمَّم قبل الكود
في `docs/DATABASE_SCHEMA.md` §3 كل عملية لها policy خاصة بها:

```sql
-- select
USING ((select auth.uid()) = user_id)
-- update
USING ((select auth.uid()) = user_id) WITH CHECK ((select auth.uid()) = user_id)
```

المعنى ببساطة: قاعدة البيانات نفسها ترفض أن يرى مستخدم مهام مستخدم آخر، حتى لو كان في كود الواجهة خطأ. سنطبّق هذا فعليًا في المرحلة 5.

### `.claude/settings.json` كخط حماية
مقتطف حقيقي:

```json
"ask": ["Bash(git commit *)", "Bash(git push *)", "Bash(vercel *)"],
"deny": ["Read(**/.env)", "Read(**/.env.local)", "..."]
```

- `ask`: يجب أن أطلب إذنك قبل الـ commit أو الـ push أو النشر.
- `deny`: لا أستطيع قراءة ملفات الأسرار أصلًا.

## 5. طريقة عمل المرحلة: كيف تتدفق القرارات

بما أنه لا توجد واجهة، فـ"التدفق" هنا هو مسار الفكرة من الرؤية حتى مهمة قابلة للتنفيذ:

1. **الرؤية** (`PROJECT_INTENT.md`): مقارنة المستخدم بنفسه فقط.
2. **النطاق** (`MVP_SCOPE.md`): ما يدخل وما يُستبعد.
3. **القواعد** (`PRD.md`): تعريفات دقيقة، مثل "الأسبوع يبدأ السبت" (BR-03).
4. **المتطلبات والقصص** (`SRS.md`، `USER_STORIES.md`): ماذا يجب أن يفعل النظام، ومن وجهة نظر المستخدم.
5. **التصميم التقني** (`ARCHITECTURE.md`، `DATABASE_SCHEMA.md`، `API_CONTRACTS.md`): أين يعيش كل شيء وكيف تتصل الطبقات.
6. **الاختبار** (`TESTING_PLAN.md`): كيف نثبت أن كل قاعدة تعمل.
7. **التنفيذ** (`IMPLEMENTATION_PLAN.md`): ترتيب المهام على 6 مراحل، مع نقطة موافقة منك في نهاية كل مرحلة.

وطبقات التطبيق التي صُمّمت هنا (وبُني أولها في المرحلة 2):

```text
components / pages  →  hooks / context  →  @/services  →  (mock أو Supabase)
                              ↓
                 features/*/lib و src/lib (pure functions لقواعد العمل)
```

القاعدة الذهبية: الواجهة لا تستورد Supabase أبدًا. فقط `src/services/supabase/*` يفعل ذلك.

## 6. القرارات التقنية

أهم القرارات (التفاصيل الكاملة في `docs/DECISIONS.md`):

- **D-01 — مستودع Git مستقل:** كان المجلد داخل مستودع Git على مستوى مجلد المستخدم كله، وهذا خطر قد يرفع ملفات شخصية.
- **D-02 — العربية أولًا (RTL) مع خيار الإنجليزية:** الجمهور عربي. الأرقام لاتينية (0–9) في اللغتين.
- **D-04 و D-05 — جدول واحد `tasks` بحقول قليلة:** لا وصف ولا أولوية ولا تصنيف. الإحصاءات تُشتق من المهام نفسها.
- **D-08 — طبقة services قابلة للتبديل:** نبني الميزات على mock في `localStorage` (المراحل 3–4)، ثم نبدّله بـ Supabase بنفس العقد (المرحلة 5). المتغير `VITE_DATA_SOURCE` يختار بينهما.
- **D-09 — التحليلات في المتصفح بـ pure functions:** سهلة الاختبار وشفافة. حدّها المقبول نحو 10 آلاف مهمة لكل مستخدم.
- **D-10 — لا مكتبة تواريخ:** نصوص `YYYY-MM-DD` وحساب بـ UTC لتجنّب أخطاء التوقيت الصيفي.
- **D-13 — الأسبوع يبدأ السبت:** ثابت واحد `WEEK_STARTS_ON = 6` يمكن تحويله لاحقًا إلى إعداد.
- **D-14 — الموافقة على مستوى المرحلة:** الموافقة تكون على المرحلة كاملة، ولا سؤال بعد كل مهمة.
- **D-18 — تأكيد البريد عند التسجيل (حسم OD-01).**
- **D-19 — استعادة كلمة المرور ضمن الـ MVP (حسم OD-02).** أُضيفت القصة US-26.

## 10. ماذا تعلمت؟

### المفاهيم الأساسية
1. **فصل "ماذا" عن "كيف":** `PRD.md` يقول ماذا يحدث (القواعد)، و`ARCHITECTURE.md` يقول كيف نبنيه. لو تغيّرت التقنية تبقى القواعد كما هي.
2. **مصدر حقيقة واحد:** القاعدة تُكتب مرة واحدة وتُشار إليها بمعرّفها. التكرار يولّد تناقضًا عند أول تعديل.
3. **حالة "لا بيانات" ليست صفرًا:** يوم بلا مهام نسبته `null` وليست 0% (BR-06). هذا قرار منتج يؤثر في الواجهة والاختبارات.
4. **الأمان في قاعدة البيانات، لا في الواجهة فقط:** RLS تحمي البيانات حتى لو أخطأت الواجهة.
5. **طبقة services كعقد:** الواجهة تعرف دوال مثل `createTask(input)` ولا تعرف هل البيانات في `localStorage` أم Supabase.

### مثال عملي
لو تقرّر لاحقًا أن يبدأ الأسبوع يوم الأحد، فما الذي يتغيّر؟
- القرار في `DECISIONS.md` (D-13) وقاعدة BR-03 في `PRD.md`.
- الثابت `WEEK_STARTS_ON` في `src/lib/dates.js` (يُبنى في المرحلة 3).
- اختبارات UT-01 وUT-05.
لا شيء في الـ components، وهذه فائدة التصميم.

### أسئلة لمراجعة فهمك
1. في أي وثيقة توجد طريقة حساب "أفضل أسبوع"؟ ولماذا ليست في `ARCHITECTURE.md`؟
2. لماذا نسبة يوم بلا مهام هي `null` وليست `0`؟ وما أثر ذلك على المستخدم نفسيًا؟
3. ما الفرق بين `FR-xx` و`US-xx`؟
4. لو أخطأ كود الواجهة وطلب مهام كل المستخدمين، فما الذي يمنع تسرّب البيانات؟
5. لماذا نبدأ بـ mock service بدل Supabase مباشرة؟
